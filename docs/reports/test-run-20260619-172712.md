## BUGS FOUND

### Bug 1 — Notes enforcement gate uses 303 redirect (no client-side validation)

**What:** Backend correctly blocks resolve without notes for red flag and identity cases (lines 4439–4447, main.py). But it uses a server-side 303 redirect to an error URL, not a 400 response. There is no client-side gate — staff click "Resolve", form submits, page reloads with an error message. On a busy day this adds friction and confusion.

**Risk:** Staff may not notice the error redirect and think the case was resolved. Medium.

**Fix needed:** Add client-side JS validation — if `red_flags_present` is true or case is identity-sensitive, disable the Resolve button and show an inline warning until the outcome notes field has content.

---

### Bug 2 — `verification_status` null for all fresh pipeline cases

**What:** All 5 cases show `verification_status = null` after the full pipeline run. The field is in the DB schema but the pipeline is not populating it.

**Risk:** HIGH. Reception staff cannot see whether the patient was matched. This is the most important field for the triage workflow. Unanswered: is this a pipeline extraction gap, a handoff JSON omission, or an importer mapping error?

**Next step:** Read `app/modules/Jeff.Handoff.ps1` and `dashboard/app/importer.py` to trace whether `verification_status` is being written to the handoff JSON and mapped on import.

---

### Bug 3 — `canonical_request_type` null for all fresh cases

**What:** The `canonical_request_type` field is null in all API responses. This field drives the request type pill/label on the dashboard. When null, the display falls back to the raw `request_type` value (e.g. "test_result" instead of "Test Result").

**Risk:** Low for function, medium for professionalism. Labels look unpolished.

---

### Bug 4 — `resolved_by` not returned in `/api/cases/{call_id}` response

**What:** The API endpoint (main.py:3299) does not include `resolved_by` in its response fields (lines 3309–3350). Staff name is written to the DB on resolve but never surfaced via the API. Case detail panel may be reading it from a separate route, but the API gap means any future API consumer or mobile client won't see who resolved the case.

**Risk:** Audit trail gap. Low for now, important for CQC compliance later.

---

### Bug 5 — `created_at` null for fresh batch cases

**What:** All 5 CSV-FRESH cases have no `created_at` value in the DB. They sort to the bottom of the worklist (below all DEMO cases from June 2026) because null sorts last. A new urgent case arriving via the pipeline could be invisible if the worklist is sorted by arrival time.

**Risk:** Medium. Could cause a staff member to miss an urgent case.

**Next step:** Check the importer — it should be setting `created_at` from the handoff JSON `timestamp` field.

## UX IMPROVEMENT SUGGESTIONS

These are all from the staff simulation — things that would slow down or confuse a real receptionist.

### 1. Resolve button should have an inline notes warning

Before staff click Resolve on a red flag or identity case, show a visible warning: "Outcome notes required before resolving this case." Disable the Resolve button until the field has content. Currently the page just reloads with an error after the failed submit — staff lose their place.

**Effort:** Low (JS, ~1 hour).

### 2. Verification status badge missing from case cards

The most-used piece of information on a triage worklist is: "is this patient verified?" Currently `verification_status` is null across the board, but even when populated, there is no tested evidence of a visible badge. Each case card should have:
- Green "Verified" — patient matched in EMIS
- Amber "Partial Match" — possible match, needs confirmation
- Red "No Match" — patient not found
- Grey "Unverified" — pipeline didn't run matching yet

**Effort:** Medium (badge component + API field).

### 3. Third-party caller badge on case card

Case 004 (Dorothy Bridge) was a daughter calling on behalf of the patient. There is no badge or visual indicator on the card that the caller is not the patient. Reception staff need to know this at a glance — it changes the ID verification procedure entirely.

Add a "Third-party caller" or "Not the patient" badge. This should be derived from the pipeline pathway detection, not a manual staff field.

**Effort:** Medium.

### 4. Red flag cases need to be unmissable

Case 005 is a 999 Emergency (meningitis signs). On the worklist, it should be visually impossible to scroll past — red border, background colour change, or a pulsing indicator. A subtle red dot is not enough when reception desks are busy and the worklist has 20+ entries.

**Effort:** Low (CSS only).

### 5. Status label "Urgent Review" should say "999 Emergency" for red flag cases

Case 005 shows `status = "Urgent Review"` and `priority = "999 Emergency"`. These two labels conflict. NHS staff know what "999 Emergency" means. "Urgent Review" sounds like a GP chart review. Use "999 Emergency" as the status display for any case with `red_flags_present = true` or `priority = 999 Emergency`.

**Effort:** Low (Jinja2 template logic).

### 6. "Assign to me" step missing from workflow

For "Needs Review" cases, the tested workflow is: start_review → fill notes → resolve. There is no visible "I am handling this" step between start_review and resolve. In a multi-staff environment, two receptionists could work the same case in parallel. An explicit "Assign to me" step (or auto-assign on start_review) prevents this.

**Effort:** Medium.

### 7. Resolved cases should show who resolved them

After resolving case 001, the case detail shows no `resolved_by` value via the API. The audit trail is incomplete. Every resolved case should show: "Resolved by [name] at [time]" visibly on the detail view.

**Effort:** Low (add field to API response, display in template).

### 8. Worklist doesn't auto-refresh

When test_user resolves a case, another staff member viewing the same worklist doesn't see it change. Add a polling refresh (every 30s) or a manual "Refresh" button with a "Last updated: X minutes ago" timestamp. Minimal implementation is a refresh button — full WebSocket is Phase 2.

**Effort:** Low (JS + timestamp display).

### 9. Request type labels should be human-readable

Raw values like "test_result", "sick_note", "appointment_redirect" appear when `canonical_request_type` is null. These are developer strings, not staff-facing labels. Fix the null fallback to always use a properly capitalised label (Test Result, Sick Note, Appointment).

**Effort:** Low (Python mapping dict in prepare_case).
